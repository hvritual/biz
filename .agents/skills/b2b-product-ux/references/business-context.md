# 八维业务上下文

这些是分析维度，不是新业务实体/权限表。每个 summary 都附 `source_refs`，来源说明是合同义务、实现事实还是设计假设；同一字段不要混称。

| 键 | 用户要回答 | 最低分析信息 |
|---|---|---|
| `role` | 我是谁，在替谁工作？ | 平台/租户身份、角色、作用域、技能水平和使用环境；权限引用可信来源 |
| `task` | 我来完成什么？ | 触发、用户目标、入口、成功/退出条件、频率；不能用“做一张页面”代替任务 |
| `entity` | 操作哪个对象？ | 主对象、关联对象、可理解名称、归属/范围；查看对象与选择集合分开 |
| `workflow` | 现在在哪一步？ | 前后步骤、参与方、交接/等待、停止条件和返回路径；复用已有流程 |
| `state` | 当前事实是什么？ | 权威业务状态、页面临时状态、数据时间、未知/延迟/冲突；不混同 |
| `action` | 能做什么，为什么不能做？ | 实际存在的操作、前提、权限/权益/额度/对象限制、批量范围、结果来源 |
| `risk` | 做错会怎样？ | 费用、权限、隐私、设备、安全、外部副作用、可逆性、并发/重复提交 |
| `decision` | 我需要选择什么？ | 做判断必需的信息、口径、已知/未知、可选路径、建议依据和需用户确认项 |

点位是数据单位，客户是经营单位。设备替换、转场及跨租户授权需引用真实归属/历史规则，不能因页面便利改变数据归属。不同角色应看到完成同一任务所需的不同信息，不因角色名称猜测权限。

经销商、客户、楼宇与点位分别按当前业务定义理解。可以复用名称/编码搜索入口，但结果需保留实体类型、身份与归属；“合并搜索控件”不授权合并业务对象或删除某类查询能力。

## 区分状态维度与可用条件

设备的连接状态、使用状态、告警情况和制作能力可能同时存在，分别核实其来源、时间及未知项。例如在线设备可以存在告警，离线设备也可能在现场正常制作；不能把这几个维度当作同一个互斥选项。视觉颜色辅助扫描，文字表达实际含义，不依靠颜色或图标独自传达状态。

租户、模块、成员和权限任务至少区分以下事实；此表说明需回答的问题，不定义新的权限模型或可用性算法：

| 事实 | 应核实的问题 |
|---|---|
| 模块可用性 | 平台是否存在并允许使用此模块？ |
| 租户权益 | 当前租户是否拥有有效权益，其来源、范围和有效期是什么？ |
| 成员权限 | 当前成员是否被授予这项操作，授权来源是什么？ |
| 对象数据范围 | 当前目标对象是否属于该成员获准操作的范围？ |

对象状态、额度、版本等其他前置条件继续按实际服务端契约执行，不能由上表推导新规则。模块配置保存、套餐生效、成员授权和实际可用性各有结果，不能统一显示“已开通”或用菜单可见证明服务端授权。无权操作的原因和申请/接管出口只展示获准信息，不为了说明原因泄露其他租户数据。

## 按行为影响分类

| 分类键 | 适用 | 最小充分检查 |
|---|---|---|
| `engineering` | 无用户行为变化的整理 | 原工程检查；不强制完整 UX 分析 |
| `ui_presentation` | 颜色、字号、间距等展示调整 | 现有设计/可访问性/视觉规则；不复制业务契约 |
| `ui_interaction` | 筛选、Tab、详情等上下文交互 | 页面状态、结果反馈、焦点、键盘及上下文恢复 |
| `backend_capability` | 非用户直接操作的 API/任务 | 后端授权、不变量、错误及真实结果；Skill 只记录交接，不做页面验收 |
| `business_task` | 人通过 UI 完成业务写操作或敏感任务 | 完整上下文、影响、结果、恢复及适用后端/任务证据 |
| `unknown` | 信息不足 | 明确缺口，先核验风险；不能按低风险默认放行 |

分类不是单看是否写数据库。只读导出敏感数据、跨租户授权呈现、支付确认或远程控制也需按风险提升。基础权限必须存在；提升指本次变更触及授权/隔离等敏感语义，不把所有普通只读详情机械升级为完整业务写任务。

## 设计前核对

从任务实际的角色与对象起步。系统已知的数据不要求重复输入，但预填值可能过期；涉及计费、归属、权限或破坏性影响时重新确认权威版本。减少页面跳转不是取消步骤，正确的目标是减少无必要的上下文重建。

`unknown` / `stale` / `no_permission` / `empty` / `no_results` / 读取失败分别表达；不把错误改成空表格，也不把未知库存或利润填零。真实空集合可按权限提供新增，筛选无结果可调整条件，无权限和读取失败分别提供实际允许的出口，不能统一显示“去新增”。套餐能力、成员权限、数据范围、对象状态和额度不是同一个开关。

需要记忆筛选、列配置或视图时，先核实存储内容及用户/租户/页面/配置版本作用域；记忆不能使旧对象、草稿或操作状态跨身份残留。返回同一列表与切换租户是不同场景，分别写入验收。具体模式见 [搜索与保存视图](b2b-interaction-patterns.md)。

## 两个范围样例

“找到成员并查看后返回”：主对象是成员、查看不改变勾选；关注筛选/分页/滚动和焦点。无需凭空增加删除确认或付款恢复。模板的 [成员示例](../examples/member-context-review.yaml) 表达设计义务，不宣称当前浏览器测试已执行。

“调整套餐”：识别当前租户与订阅，核对当前/目标、差额、额度、权限、生效方式及结果来源。当前契约未提供报价/支付/权益回读时标记缺口，不添加可执行付款按钮；已有业务规则不因设计分析改变。

## 事实不足时

先查当前源码、接口和已有决定；仍缺失则记录 `open_questions`，说明是否阻塞、哪个角色提供证据、可以继续的只读工作。允许给明确标注的设计假设，但不能据此执行高风险操作或宣称用户问题已解决。
