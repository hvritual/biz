# Humanized B2B UX：九维

本文件是九维术语和设计义务的规范入口；模板只承载每个任务的选择与证据。九维不是九个必放 UI 模块，也不是一套可求平均的 UX 得分。每维区分适用性、实现义务和实际验证。

## 1. Time to Information — `time_to_information`

用户进入任务后，多久能够找到并正确理解关键事实，而不是页面加载耗时。先给对象、当前状态、首要问题及数据范围/时间，再按需展示技术资料；不要默认把所有指标置顶。

验证：静态/浏览器只能说明信息是否存在、可见和可访问；识别时间需真人任务测试，明确起点、目标事实、答对标准、角色、设备及失败/放弃样本。无样本不写 0 或 PASS。

## 2. Time to Action — `time_to_action`

在用户理解问题后，进入正确且允许的下一动作所需的时间。问题与相关动作靠近；不可执行时说明原因和实际可用出口。远程指令要求设备在线时，离线页面不能以假诊断按钮营造方便。

验证：用浏览器测可达路径、可用状态；用户判断时间另测。不能为缩短路径删除身份确认、影响预览和必要审批。

## 3. Context Switching — `context_switching`

减少任务中无必要的切页、模块跳转及返回后的上下文重建。保留适用的对象、筛选、排序、分页、滚动、选择和焦点；切租户/身份时必须清理旧上下文，而不是永远保留。

验证：打开/关闭详情、返回列表、刷新和身份切换分别测试。查看不等于勾选。跨页次数只是辅助指标，不能统一规定两次以内。

## 4. Decision Load — `decision_load`

将事实、含义、影响、未知与可选下一步组织成用户能判断的内容；显示建议的依据和替代解释，不把决定权藏进默认选项。不完整证据不输出确定根因、损失金额或客户流失判断。

验证：来源/口径可审查；真人能解释“为何做/不做”及操作后果才是理解证据。更多建议、更多提示不自动降低负担。

## 5. Interaction Cost — `interaction_cost`

计算点击、输入、选择、等待、切页、重复录入及人工核对。复用可信已有数据，安全预填，支持真正有价值的批量操作；明确全选是当前页、当前筛选还是全量对象。

验证：任务正确完成率、误操作与返回路径和操作量一起评估。不能只奖励点击变少；高风险任务增加必要确认可以是改进。

## 6. Error Recoverability — `error_recoverability`

系统操作失败或结果不确定时，保留输入，说明已知结果、未知部分及安全下一步。区分校验、权限、权益、额度、状态冲突、并发、网络超时和异步处理。

写请求超时不等于未执行：先用实际 operation/status/readback 契约核验；只有幂等/重试规则允许才重试。没有状态查询入口时保留操作信息并转给支持，而不是编造接口。不可撤销的动作给补偿/接管路径，不虚构 Undo。

验证：故障注入、真实错误码映射、原操作标识/草稿保留、重复请求安全和最终状态；不能只断言出现 toast。

## 7. How-to Guidance — `how_to_guidance`

对应用户提出的 **How to do**：不知道怎么做时，在任务现场获得必要指引。简单任务可一句话，复杂任务按需展开步骤；熟练用户无需反复走新手导览。

需要步骤时至少描述：触发与目标、谁可操作、前置条件、步骤与每步观察结果、停止条件、完成验证和真实接管出口。耗时只有来源/测量支撑才展示，未知则不估成确定值。

设备指引还需适用机型/软件版本、审核来源和有效性；无已核验材料，不编造错误码、清洁/拆机/维护步骤。普通运营者不承担专业维修。重要帮助能用键盘打开，关闭后回到任务，不丢输入。

验证：用户能按指引完成获准步骤或正确转交；有文字/图标不是完成证据。

## 8. Operation Effect Transparency — `operation_effect_transparency`

对应 **Operate Effect Tip**：操作前说明会发生什么，操作后说明实际上发生什么。

操作前：对象和范围、当前→目标差异、生效方式、费用/额度/权限/通知等适用副作用、可逆性与未确定项。按风险分级：普通筛选不需要模态确认，删除/计费/远程动作需适当确认。

操作后：分别呈现请求受理、排队/处理中、部分成功/失败、最终状态、权威回读与未完成项；异步任务有真实可达进度出口。费用/状态/影响来自现有契约，Skill 不推算。

关键后果不能只在 hover tooltip 或自动消失通知中；操作标签说清动作。不得无依据宣称移除成员释放额度、登录立即失效、扣款绝不重复或操作可回滚。

验证：影响预览与服务端允许/实际变化一致；用户能说明后果；最终结果与 readback 对应。

## 9. Problem Resolution Guidance — `problem_resolution_guidance`

对应 **Operate Problem solution tip**：处理业务问题，而不只是处理界面报错。链路为问题→已知事实→可能原因/待核实→验证→允许动作→责任人/接管→解决条件。

设备离线、账单争议、服务未恢复等场景，即使系统请求正常，也可能没有解决。依证据分流；无法判定根因时先核实，不连续制造同一问题的重复事项。

业务恢复条件引用真实服务端事实或有效人工确认；“创建工单”“维修人员提交”“设备重新在线”不能彼此冒充最终服务恢复。

验证：从发现到结束/接管的任务证据。与第六维可共用处理步骤和组件，但入口不同：系统失败/不确定结果，与业务问题持续存在。简单查列表可有理由地标本维不适用。

## 提示强度与证据规则

提示按必要性分层：关键决策/费用/危险后果直接展示；步骤在任务中按需展开；深入解释可折叠。无权限内容只暴露获准信息，不借“透明”泄露敏感数据。遵守现有可访问性、中文/英文长文案和缩放规则，不为密度缩小必要信息。

本体系的 3 秒、5 秒、两次切页等历史讨论数字不是默认标准。各任务先定义测量和基线，再由 Owner 确认目标。自动化结果、真人观察和业务真实性不可相互代替；不使用“存在一个 true 字段”作验收。
