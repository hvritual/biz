# 任务推进反例：把本次失误变成下次检查输入

来源：#331 模块管理旅程复盘；规则集成任务 #332。历史对话说明问题类型，不是当前仓库缺陷的永久结论；使用具体案例前重新读取目标候选与真实证据。本文件不重新认证历史 PR、CI 或生产效果。

这里是反例与验收要求，**不是已经运行的自动化测试**。当前防护层是根 AGENTS + [任务推进 Skill](../SKILL.md) + 人工/Agent 按阶段核对。下列自动断言需后续实现并获得真实失败/修复证据。

| 反例 | 应在哪个阶段发现 | 应拒绝的替代结论 | 正确处理及后续自动检查的预期 |
|---|---|---|---|
| 原始任务包含新增，计划只剩列表/编辑/状态修改 | 需求、能力核对、每次续跑 | “已有页面功能都做了，所以完整” | 保留稳定任务 ID，核对创建契约与实现；缺少必做任务使覆盖检查失败 |
| 已有创建接口，因前端没有封装而报告后端不存在 | 能力核对 | “后端没能力，所以不设计新增” | 逐项查 Operation、服务实现、前端接线；区分未接入和不存在 |
| 将创建已注册模块目录与随意创建技术定义混为一谈 | 需求、设计 | “不允许任意定义，所以禁止所有新增” | 分清对象和能力边界，依据现有注册/创建契约设计合法路径 |
| 建立/调整关联的要求被只读列表替代 | 需求、设计、验收 | “有‘关联页面’标签，所以关系管理完成” | 对比用户要求的可观察效果；无权威变更与生效路径不能通过 manage 验收 |
| 显示权限标识就宣称当前主体已获授权 | 设计、验证 | “权限字符串可见，所以可执行” | 区分定义、角色授权与运行核验；需要实际主体/范围/动作的授权证据 |
| Mock 对所有写操作都 version+1，或默认状态绝不联动 | 契约核对、实施、验证 | “模拟 E2E 通过，所以服务语义正确” | 每个 Operation 对照真实业务规则；用版本不变/联动变化的合法场景暴露错误假设 |
| 将真实必做任务改成 skipped，或把‘尚未接入’设为完成条件 | 实施、验证、交付 | “测试全部绿，所以完整” | 保留未完成任务；验收弱化必须有真实范围批准，不能自行删除断言 |
| 增加视口与截图，掩盖任务缺失 | 设计、交付 | “52 张图等于52种已完成操作” | 任务覆盖与视觉覆盖分别统计；截图数量不改变任务分母 |
| 点击后详情在视口外，没有观察实际结果 | 验证 | “点击成功且截了图，所以操作结果已呈现” | 浏览器断言目标状态可见/可达，再收集操作结果证据 |
| 修改目标、契约、实现或期望，继续使用旧候选审阅 | 每次续跑、验证、交付 | “之前通过过，所以现在仍通过” | 核对当前候选、基线与外部批准；复核/重跑受影响证据，保留失败历史 |
| 执行者自己写 approved 或 Done，改题再改答案 | 评审、交付 | “文件里写了批准，所以已批准” | 外部批准来源/身份/候选独立核验；文档字段不是授权 |
| 新增规则文件但没有入口/执行器接线 | 复盘、后续启动 | “Skill 文件存在，所以每个 Agent/CI 自动强制” | 核对加载链；分别报告规则落盘、入口接线、自动检查、实际测试、main 状态 |

## 检查器的反向验收方法

未来实现确定性检查时，必须在隔离测试副本中分别植入上述相关错误，证明检查失败；再用符合契约的修复证明通过。不得在生产数据上制造故障，不改弱现有门禁，不凭关键词检查宣称已解决语义完整性。

范围基线和预期结果需从被测实现以外的批准来源读取；如果测试生成器与实现者共用错误假设，换模型或增加断言数量不构成独立验证。

## 本轮边界

本轮只把反例接入阶段核对与交接，未实现新的范围差异检查器、Mock 行为一致性验证器、逐按钮运行鉴权或自动合并阻断。既有工具只按各自已验证能力使用。上述缺口保留，不能因规则文档已提交而勾选为技术能力已完成。
