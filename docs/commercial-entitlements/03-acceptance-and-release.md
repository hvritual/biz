# 03 验收矩阵与发布资格

## 1. 验收来源与状态

本表是未来任务的验收要求，**不是已执行测试结果**。测试数据必须隔离、可清理、不含生产个人信息；允许测试层故障注入与受控设备模拟，不允许生产路径 mock/fallback。

## 3. 已有命令：执行前满足真实依赖

已在固定基线 Makefile 核验以下目标；本次文档交付不执行它们，也不声称它们已经通过。

```sh
# 仓库根目录；先准备仓库锁定的 Yunka 兄弟目录、Go/protoc 工具链。
make yunka-source-check
make workspace-check
make generate
make check
make test
make verify
make consumer-certify

# 必须是可用的隔离 MySQL 数据库；DSN 由环境安全注入，不写进仓库。
# Makefile 的 pressure 使用 YUNKA_TEST_MYSQL_DSN。
make pressure

# Linux 环境下的现有封装边界回归。
make tenant-boundary-check
```

前端命令只在 CE-11 接受并集成对应 web 基线后使用：

```sh
cd web
npm ci
npm run check
npm run test:e2e
```

`npm run check` 包含类型、Lint、架构、单元测试和构建；E2E 使用真实浏览器。API 模式与 preview 模式测试需分开，preview 通过不能代替正式接口联调。

## 4. 拟新增的任务级测试约定

每张任务卡声明 `TestCE##_...` 或 `CE-##` E2E tag，这是 **要求任务实现时创建的测试标识**，当前不保证对应文件／测试存在。后端示例：

```sh
# 仅在任务实际添加测试后执行；范围及 build tags 随回执列明。
go test -json -count=1 ./... -run '^TestCE05($|_)'
go test -json -count=1 -tags=integration ./integration -run '^TestCE19($|_)'
```

任务回执必须统计匹配测试数且大于零；`[no tests to run]`、空 grep、只跑构建均不能作验收。若测试位于不同包，应在回执写真实命令和原因，而非硬凑示例路径。

前端任务应增加可定位的 Playwright 用例，例如 `CE-14 tenant switch ignores stale response`；记录实际用例数、截图和错误注入。1366×768、1440×900、390×844 检查布局；保留 480px 双列浮层、不推动内容区与键盘焦点路径。

## 5. 质量与性能证据

CE-25 至少记录单租户／多租户、单实例／多实例、读写混合、套餐切换竞争、最后名额竞争和缓存异常。记录硬件、并发量、请求数、错误率、p50/p95/p99、数据库／锁等待、检查前后差值，不写没有实际基线支撑的性能承诺。

撤权以“生效提交后开始的新请求”及任务声明的严格写屏障分别定义观察边界；不能用一次页面刷新成功证明一致性。异步通知与轮询只是 UI 同步，不承担服务端授权保证。

## 6. 发布与证据边界

里程碑要求见 tasks.json 的 profiles 和 [路线图](02-roadmap.md)。所有必需任务 DONE、证据齐全、外部条件满足后才允许宣称对应资格。CE-22／23 未完成不阻塞核心订阅功能，但相关入口不得对外标注可生产使用。

新功能可以先做可观测对照与指定试点启用；已经启用的租户不能因错误回滚策略变成全放行。数据库迁移采用向前兼容和补偿版本，审计保留；涉及不可逆外部操作时记录限制，不伪称可以完全撤销。

最终集成后在 main 的真实 SHA 上回读文档、执行受影响回归并核对运行版本。不能仅以 PR 创建、HTTP 200、支付返回页或 commit 对象存在宣称交付完成。
