# C10.4 — Consumer Upgrade

## Status

- State: **In progress**
- Consumer base: qualified C9.9 branch `agent/c9-9-conformance-closure@1c66672ba981c083a84997e0dbbd23331905f9cb`
- Framework target: qualified Yunka C10.3 exact head `561d9c779334371735acf8d394969cb752e3999d`
- Yunka tracking: issue #50 / Draft PR #51

## Goal

Migrate the real DeviceOps consumer onto the C10 Runtime Assembly path while preserving the C9.8/C9.9 cross-Application truth.

```text
device.transfer
  -> site.validate_transfer_target
  -> handwritten business decision
  -> device.update
```

The migration is not permission to move Biz-specific behavior into Yunka.

## Before inventory

### Structural framework plumbing currently handwritten

`cmd/biz/main.go`:

- App construction via `kernel.New` + default module catalog;
- explicit App Start/Shutdown sequencing.

`modules/deviceops/module.go`:

- Security/Executor construction;
- handwritten Application instance wiring;
- handwritten child-capability wiring;
- manual canonical REST registration;
- manual canonical gRPC registration;
- HTTP/gRPC listener/server lifecycle bookkeeping;
- module-owned server health and graceful shutdown.

### Consumer-owned code that must remain handwritten

- environment and secret loading;
- platform/database configuration;
- access bootstrap and data migration;
- authentication middleware/interceptor implementation;
- Device OperationGuard construction and product policy interpretation;
- repository factory and business Application constructors;
- listener addresses/TLS/process configuration;
- business use-case decisions.

## Preserved C9 truth

- `site.validate_transfer_target` remains an internal canonical Operation with no REST/gRPC binding;
- generated typed child capabilities use `ExecuteChildTyped`;
- root `device.transfer` has explicit transitive permission closure;
- one root authorization decision;
- one root local UoW/ExecutionScope;
- no nested child transaction or child root authorization;
- no direct cross-Application repository/service-locator bypass;
- internal-only DTOs remain absent from external projections unless externally reachable;
- idempotency/Saga/Outbox semantics remain unchanged.

## Pressure classification

Every blocker is classified before framework changes:

- **P0 Compiler defect** — already-declared C10/C9 semantics cannot generate correctly;
- **P1 Missing generic assembly seam** — structural wiring remains but current typed C10 bindings cannot express it;
- **Consumer-specific** — keep it in Biz;
- **Deferred framework pressure** — record it; require another independent proof before adding semantics.

## First executable baseline

Before changing Biz runtime wiring:

1. checkout this exact Biz branch and Yunka C10.3 exact head side-by-side;
2. run current Biz `make verify` against C10.3;
3. run current Biz MySQL 8.4 `make pressure` against C10.3;
4. copy Biz to a temporary sibling working tree;
5. run Yunka C10 `assembly generate` into that temporary consumer;
6. run `assembly check`;
7. run a second generation and require byte-for-byte generated assembly zero drift;
8. compile/test the temporary consumer with generated assembly present.

This baseline answers whether C10 can consume the existing qualified contract/module facts before any migration workaround is introduced.

## Completion gate

C10.4 is complete only after the committed consumer migration:

- regenerates through C10 contract + assembly generation;
- has second-generation zero drift;
- passes `make verify`;
- passes MySQL 8.4 `make pressure`;
- preserves cross-Application/authz/UoW/internal-operation assertions;
- has zero manual canonical REST/gRPC registration for migrated Operations;
- has no Application-level framework authorization or transaction bypass;
- records before/after plumbing inventory and all remaining pressure.
