## Before inventory

### `cmd/biz/main.go`

Before C10.4:

- manually selected the process-global/default module catalog;
- called `kernel.New` directly;
- started/shut down the App outside generated assembly.

### `modules/deviceops/module.go`

Before C10.4 the module manually owned:

- Security/Executor construction;
- Application instance wiring;
- child-capability wiring;
- canonical REST registration;
- canonical gRPC registration;
- HTTP/gRPC listeners and servers;
- server health bookkeeping;
- graceful server shutdown.

This mixed module capability declaration, consumer-specific initialization and process runtime assembly.

## After inventory

### Generated assembly now owns structural wiring

`internal/assembly` owns:

- explicit generated module catalog creation;
- deterministic Application build order;
- generated typed child capabilities;
- canonical REST registration;
- canonical gRPC registration;
- runtime route/RPC inventory;
- generated Bootstrap into existing `kernel.Bootstrap` / `core.App`.

### `modules/deviceops.Module` is narrow

The module now only validates the generated descriptor's typed capability view and implements `modulecatalog.Instance.Name()`.

It no longer owns:

- Executor construction;
- child Application wiring;
- REST/gRPC registration;
- listeners/servers;
- process health;
- server shutdown.

### Biz-owned `internal/bizruntime`

Biz intentionally retains:

- process configuration and secrets;
- database configuration;
- schema/data migration;
- access bootstrap;
- bearer authentication middleware/interceptor;
- Device OperationGuard/product scope interpretation;
- canonical C9 Security/Executor construction;
- repository and handwritten Application constructors;
- explicit listener addresses.

It supplies those consumer facts through generated `RuntimeBinder`, then generated assembly performs Application dependency and transport wiring.

HTTP/gRPC lifecycle is adapted through the existing Yunka runtime components and is owned by the same `core.App` lifecycle.

`/healthz` now adapts `core.App.Health` rather than maintaining an independent module-health model.

## Framework pressure disposition

### No P0 compiler defect

The unmodified qualified C9.9 contract/module facts compiled through C10.3 assembly on the first executable baseline. No contract workaround or business-semantic DSL extension was required.

### C10.4-P1-001 — post-Platform typed runtime binding

Real Biz proved that its canonical Executor depends on the App-owned `primary` database, which exists only after `kernel.New -> Platform.Prepare`.

C10.4 added the smallest generic seam: generated `RuntimeBinder` runs inside the existing Bootstrap Build callback after Platform preparation and returns only typed `ApplicationFactories + operation.Executor`.

It does not create a second runtime, call Platform.Prepare, discover services, or own authorization/transaction lifecycle.

**Status:** CLOSED.

Detailed pressure evidence is in `docs/pressure/C10-framework-pressure.md`.

Historical FP-C9-005 Saga topology remains deferred; C10.4 supplied no reason to promote it.
