# 成员、权限与通知 UX 验收方案

状态：待真人可用性测试。本文不把自动化检查或预览数据当成用户研究结果。

## 目标与边界

目标用户是企业所有者、HR/行政和业务主管。操作应在当前列表或编辑面板完成，避免为了高频任务跳到另一层页面。所有写入仍以服务端会话、权限、幂等键、版本校验和读回为准；前端不能把无权操作显示为成功。

当前界面已提供成员列表内的新增/邀请、批量启停、详情抽屉、角色复制、分组权限全选、变更前校验和通知偏好确认。真实 API 目前**没有管理员密码重置命令**，通知偏好契约目前只有当前企业的可选短信/邮件开关。因此密码重置、通知类型订阅和接收频率不能用纯前端伪造为“已上线”。

## 核心任务收敛到三步

| 任务 | 入口 | 三步路径 | 必须的前置反馈 |
| --- | --- | --- | --- |
| 新增/邀请成员 | 成员列表的“新增成员”或“邀请成员” | 1. 填身份和联系方式；2. 选组织、角色与激活方式；3. 创建并读回结果 | 即时校验账号、联系方式、激活方式和额度；明确链接/短信的下一步与有效期 |
| 编辑/调整成员权限 | 成员行“编辑”或“更多 → 变更角色” | 1. 打开当前成员；2. 勾选角色/范围并查看变更前后；3. 保存并读回 | 最后所有者、失效角色、版本冲突均在提交前阻断 |
| 移除成员 | 成员行“更多 → 移除并交接” | 1. 选择移除；2. 填原因并确认影响；3. 完成后显示回收站入口 | 明示角色、数据访问和会话影响；最后所有者必须先交接 |
| 批量启停 | 列表勾选后的工具栏 | 1. 勾选同状态成员；2. 填原因并确认；3. 提交并刷新当前页 | 不允许混合状态、重复选择或触及最后所有者；失败对象要逐个指出 |
| 新建/编辑角色 | 角色列表的“新建角色”或行内“编辑” | 1. 填角色和数据范围；2. 在权限矩阵中选择；3. 保存并读回 | 分组计数、全选/半选状态、变更后的可用权限目录与保存前复核 |
| 复制角色 | 角色行内“复制” | 1. 点击复制；2. 改名称并确认权限/范围；3. 保存并读回 | 内置角色只允许复制为自定义角色；不可把复制误解为直接授予成员 |

权限项没有天然顺序，拖拽会引入误操作且不利于键盘用户。因此此处用“分组矩阵 + 全选/半选 + 分组快捷定位 + 已选计数”替代装饰性的拖拽。若未来出现“优先级排序”这一真正有序的业务概念，拖拽必须有键盘等效操作、放置提示和撤销。

## 界面与交互准则

- 高频入口：新增、邀请、批量启停、导出保留在成员列表工具栏；查看、编辑和更多操作保留在对应行，避免层层跳转。
- 批量操作：只对当前筛选页的显式选择生效；工具栏持续展示选择数，确认弹窗列出目标姓名、原因、影响和不可操作原因。
- 权限配置：按业务域分组；组头显示 `已选/总数`，全选框应支持半选；每个权限项同时提供人能理解的名称和最小范围说明。保存前重新读取权限目录，避免陈旧权限被写入。
- 复制：当前已经支持“复制角色”。“复制成员权限”应作为后续 API 能力：选择来源成员和目标成员后，只复制角色绑定，不复制个人资料、登录状态、MFA、业务范围或安全凭据；提交前显示来源、目标、将增加/移除的角色与最后所有者保护。
- 反馈：写入中使用明确进行态；成功只在服务端读回后显示；不确定结果只提供“核对本次修改”，不能鼓励重复提交。

## 用户故事与功能验收标准

### 成员管理

#### US-M01：邀请一名新成员

作为 HR/行政，我希望直接从成员列表邀请同事并一次完成角色与激活方式设置，以便不必在多个页面之间往返。

验收标准：

1. 已具备邀请权限的用户在成员列表首屏可见“邀请成员”；无权限用户既看不到入口，也不能通过深链打开写入弹窗。
2. 点击入口后，身份与联系方式、组织与角色、激活方式在同一弹窗内完成；从打开到成功反馈不超过 3 个用户决策步骤。
3. 提交前即时校验账号长度/格式、重复邮箱或手机号、至少一个有效角色、激活方式和短信激活所需手机号；错误紧邻字段且描述可执行的修正方式。
4. 提交期间主按钮不可重复触发；服务端读回成功后才关闭弹窗并显示成功反馈。读取失败或结果不确定时保留弹窗、显示“核对结果”，不得显示成功。
5. 激活方式说明收件渠道、用户后续动作及链接/初始口令的有效期；预览模式必须明确标记为预览，不得声称真实消息已发送。

#### US-M02：在成员上下文中调整角色

作为业务主管，我希望从成员行直接调整某人的角色，并在保存前看懂权限影响，以便避免授予错误权限。

验收标准：

1. 有角色变更权限时，成员行的“更多”菜单提供“变更角色”；详情抽屉也提供同一动作，二者打开同一配置语义。
2. 用户在同一弹窗内选择角色并看到变更前/后的角色和数据范围摘要；有效角色为空、角色被停用或成员已移除时，保存被前置阻断并说明原因。
3. 最后一位企业所有者不能被降权、停用或移除；提示必须说明先完成所有者交接，而不是仅显示通用失败。
4. 保存使用成员版本进行并发校验；发生冲突时不覆盖他人更新，并引导重新读取后再选择。
5. 真实服务由角色派生数据范围时，界面不得暗示可以单独覆盖成员范围；实际业务范围的编辑需进入已授权的范围配置面板。

#### US-M03：批量启用或停用成员

作为 HR/行政，我希望勾选同一状态的多名成员后一次完成启停，以便减少重复确认。

验收标准：

1. 列表勾选后，工具栏持续显示选择数量；未选中成员时批量按钮禁用。
2. 仅当全部选中对象处于可转换的同一状态时对应批量操作可用；混合状态、过期版本、重复选择或最后所有者必须在提交前逐项说明。
3. 确认弹窗显示选中成员、所执行动作、必填原因和影响确认；未填写原因或未确认影响时不能提交。
4. 批量请求只作用于当前页的显式选择，完成后清空选择并刷新读回数据；部分失败时刷新实际状态并逐个报告失败对象，不得把整批显示为成功。

#### US-M04：安全移除成员

作为企业所有者，我希望在移除成员前了解其访问影响并保留可恢复入口，以便安全地完成离职交接。

验收标准：

1. 移除入口在对应成员的“更多”菜单中，且只向有权限的用户展示。
2. 确认界面明确列出角色、数据访问、会话影响、必填原因和不可逆提示；用户必须主动确认后才可提交。
3. 最后所有者、已移除成员、版本冲突或无权限均不可提交，并显示针对性恢复路径。
4. 成功读回后，成员不再出现在正常列表；具备权限者可从回收站看到并按既有权限、原因和版本保护执行恢复。

### 角色与权限

#### US-R01：以可理解的矩阵配置角色

作为企业所有者，我希望按业务域查看和选择权限，以便快速核对角色的授权边界。

验收标准：

1. 角色编辑页按业务域展示权限组；每组显示“已选/总数”，并提供组级全选和半选状态。
2. 每项权限同时展示可理解的名称和简短用途；用户可通过分组快捷定位，而不需要滚动查找全部权限。
3. 全选、取消全选和逐项选择均可仅用键盘完成；焦点可见，复选框状态能被辅助技术读取。权限无天然排序时不得把拖拽作为唯一操作方式。
4. 保存前重新读取可配置权限目录；若某权限在编辑期间被撤回，系统移除该项、说明变化并要求用户再次确认，不能静默写入陈旧授权。
5. 保存成功必须以服务端读回为准；内置角色只读，用户可复制为自定义角色但不能直接修改或禁用。

#### US-R02：复制已有角色作为模板

作为企业所有者，我希望复制已有角色后只修改差异，以便快速创建相近岗位角色。

验收标准：

1. 自定义角色行内可见“复制”；内置角色的复制结果始终是新的自定义角色，不继承受保护身份或成员关联。
2. 复制后必须要求新的唯一名称；原角色的权限、数据范围和启用状态以可编辑草稿呈现。
3. 保存前仍执行与新建角色相同的权限目录、名称冲突、会话和读回校验。
4. 复制操作不改变来源角色，也不自动为任何成员授予新角色。

#### US-R03：复制成员权限（待服务端命令）

作为业务主管，我希望把来源成员的角色绑定复制给选定成员，以便快速完成同岗授权，同时不复制身份和安全信息。

验收标准（依赖后端提供批量成员角色替换/合并及逐项回执）：

1. 入口要求明确选择一个来源成员和一个或多个目标成员；来源成员不得同时是目标成员。
2. 提交前展示来源角色、每名目标成员的新增/移除角色、数据范围摘要及最后所有者保护结果。
3. 操作只能复制角色绑定；不得复制姓名、联系方式、密码、MFA、登录会话、员工信息、个人通知偏好或成员级业务范围。
4. 任一目标不具备可分配的有效角色、版本已变化或会造成最后所有者降权时，该目标被阻断并明确原因；批量结果按成员逐项读回。

### 密码重置与通知

#### US-S01：管理员发起密码重置（待服务端命令）

作为企业管理员，我希望安全地为无法登录的成员发送一次性重设指引，以便帮助其恢复访问而不接触密码本身。

验收标准（依赖真实密码重置命令、投递回执、限流和审计）：

1. 仅有受权管理员可见入口；已移除成员、无可用收件渠道或受保护账号必须在触发前说明不可执行原因。
2. 管理员核对脱敏收件地址、填写原因并确认影响后提交；全程不显示、保存或传输旧密码/新密码/验证码。
3. 请求被受理后显示请求编号、脱敏投递地址、有效期和“不要转发链接或验证码”的安全提示；同一请求不得因重复点击创建多次。
4. 投递失败、限流、链接过期和会话变化分别提供可理解的恢复操作；成功仅在服务端确认请求/投递状态后展示。
5. 每次发起和重试均写入可追溯审计记录，包含操作者、目标、时间、原因、请求编号和结果，不记录秘密信息。

#### US-N01：维护当前企业的可选通知偏好

作为成员，我希望分别决定是否通过短信或邮件接收当前企业的可选通知，以便减少无关打扰且不影响安全验证。

验收标准（当前契约可覆盖）：

1. 页面明确展示当前企业和当前账号；切换企业或账号后，旧请求被作废且不更新新上下文。
2. 短信和邮件分别显示当前状态、作用范围和开关；安全验证类消息明确不受这些开关影响。
3. 修改任一开关前显示确认和影响；提交期间不可重复写入，成功仅在读回确认后显示。
4. 冲突、无权限、会话失效、结果不确定和读回失败均保留最后确认状态，并提供“重新读取”或“核对本次修改”，不得假设保存成功。

#### US-N02：按类型、渠道和频率订阅通知（待扩展契约）

作为成员，我希望按通知类型选择渠道和摘要频率，以便重要消息及时到达、普通消息不过度打扰。

验收标准（依赖通知类型、频率、投递策略和审计契约）：

1. 偏好界面将安全、重要和常规通知分开；安全类标记为不可关闭并解释原因。
2. 重要类支持即时或每日摘要；常规类支持即时、每日摘要、每周摘要或关闭；不允许出现与该通知类型不兼容的渠道或频率。
3. 每项保存前展示“类型 × 渠道 × 频率”、作用企业和账号；保存后逐项读回并显示生效状态。
4. 同一普通事件在同一渠道和摘要窗口内至多触达一次；安全事件的多渠道投递必须解释其安全必要性。
5. 任意通知正文都能让用户准确找到背景、所需动作、时效和入口；入口必须是可访问的可见操作，而非裸链接或技术错误码。

## 密码重置：信息触达文案与状态

管理员密码重置在真实服务接入前应保持不可用并解释原因；预览模式的提示也不得暗示真实邮件或短信已发送。服务端提供命令后，采用以下触达链路：

| 节点 | 用户可见文案 | 用户下一步 |
| --- | --- | --- |
| 触发前 | `向 {姓名} 发送重设密码链接。链接将在 {时长} 后失效；为保护账号，不会显示或发送旧密码。` | 核对收件邮箱/手机号，填写原因并确认 |
| 提交中 | `正在安全地创建重设链接…` | 保持当前页，避免重复点击 |
| 已受理、待投递 | `请求已受理。我们正在向 {脱敏地址} 发送链接；请勿重复提交。` | 允许查看投递状态 |
| 投递成功 | `重设链接已发送至 {脱敏地址}，将在 {时长} 后失效。若不是本人操作，请立即联系管理员。` | 提供“返回成员列表” |
| 链接过期/失败 | `该链接已失效或未能送达。请重新发起一次，不要转发链接或验证码。` | 一键重新发起，保留操作原因 |

安全底线：只显示脱敏地址；不回显口令或验证码；有速率限制和原因审计；密码或会话变化后说明哪些会话将失效。

## 通知：渠道、层级与克制原则

| 优先级 | 示例 | 默认渠道 | 文案应包含 |
| --- | --- | --- | --- |
| 紧急/安全 | 密码重置、异常登录、权限被移除 | 站内 + 邮件；短信仅在绑定且策略允许时 | 发生了什么、影响、时效、唯一入口、反钓鱼提示 |
| 重要需处理 | 邀请待激活、审批、角色变更待确认 | 站内 + 邮件 | 背景、要完成的动作、截止时间、直接入口 |
| 常规 | 报表、订阅事项、一般更新 | 站内为主，可选邮件摘要 | 背景、是否需要动作、摘要频率和退订入口 |

个人偏好应按“通知类型 × 渠道 × 频率”表达：安全类不可关闭；重要类可选即时或每日摘要；常规类可选即时、每日摘要、每周摘要或关闭。每次修改都要标示作用企业、作用账号、是否为可选通知，并在读回确认后提示成功。当前实现仅有可选短信/邮件开关；类型和频率必须待后端契约、投递策略及审计能力就绪后启用。

统一通知句式：`因为{背景}，请在{时效}前{动作}。` + `入口：{可见动作}`。不以“系统异常”“操作失败”等技术术语替代用户可执行的信息。

## 可用性测试与验收记录

### 受试者与任务

招募 20 人：企业所有者 5、HR/行政 5、业务主管 5、首次使用的受权管理员 5。每人使用独立测试租户并完成：邀请成员、编辑成员角色、批量停用并复原、新建或复制角色、发起密码重置、调整通知偏好、从一条通知找到并完成目标动作。任务顺序应轮换，避免学习效应。

记录每项任务的开始/结束时间、完成/放弃、误操作、是否需要协助、SUS 或 5 分满意度、对密码重置说明的复述、对通知背景/动作/时效/入口四项的提取。不得用员工姓名、手机号、真实验证码或生产通知进行测试。

### 判定规则

- 核心成员/权限任务成功率：20/20（100%）。
- 与改版前同一任务基线相比，完成时间中位数至少降低 40%；计算式为 `(基线中位数 - 改版中位数) / 基线中位数`。
- 密码重置流程理解：20/20 能正确说出收件对象、有效期、下一步和“不要转发链接/验证码”。
- 通知核心信息获取：四项提取正确数 / 总项数不低于 95%。
- 过度打扰：记录每人对同一事件收到的渠道数；安全事件允许多渠道，普通事件不得因同一事件重复打扰。

- 成员端到端用例已定义批量启停、详情焦点回归、租户切换和移动端无横向溢出；本机无法运行，因为 Playwright Chromium 不支持当前 macOS 版本且没有可用系统浏览器。产品设计浏览器连接同样没有可用实例，因此本轮没有把历史截图作为审计证据。
- 因此本文件中的体验指标尚无真人结果，不能声称“效率提升 40%”“成功率 100%”或“理解率 100%”。完成 20 人测试并记录原始数据后，才可填报这些结论。
